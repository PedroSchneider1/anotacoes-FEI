# Fundamentos e Taxonomia de Testes de Software


## Por que testar software?

Basicamente para garantir a qualidade do sistema, algo adequado ao uso ou ao que se espera (no caso do software, antender aos **requisitos** estabelecidos).  
Também é importante garantir que não tenhamos retrocesso, pois ao implementar novas funcionalidades ficamos suscetíveis à erros e a prejudicar outras funcionalidades do sistema que antes funcionavam normalmente.

O que é um software de qualidade?
> "Software de qualidade é aquele em conformidade com os requisitos
funcionais e de desempenho declarados, com padrões de
desenvolvimento documentados e com características implícitas
esperadas de todo software profissional."
— Roger Pressman

Como garantir que o software atenda à esses critérios?
| **Qualidades Externas**               | **Qualidades Internas**                       |
|---------------------------------------|-----------------------------------------------|
| Funcionalidade (ele faz o que deve?)  | Eficiência (usa bem os recursos?)             |
| Confiabilidade (funciona sem falhas?) | Manutenibilidade (é fácil de evoluir?)        |
| Usabilidade (é fácil de usar?)        | Portabilidade (funciona em outros ambientes?) |

## Terminologia Básica

Erro ≠ Defeito ≠ Falha

Definição:

- **Erro**: ação humana que produz um resultado incorreto (algo humano incorreto que foi imputado)
- **Defeito**: imperfeição no código que pode causar comportamento incorreto (um comportamento não adequado)
- **Falha**: desvio observável do comportamento esperado durante a execução (manifestação do defeito)

### EXEMPLO
Cenário em um e-commerce:
>**Erro**: desenvolvedor entende errado a regra "10% de desconto acima de R$100".
**Defeito**: o código aplica o desconto em qualquer valor, não só acima de R$100.
**Falha**: cliente compra por R$50 e recebe desconto de R$5 indevidamente.

>Nem todo defeito causa falha: o trecho com defeito pode nunca ser executado.


Verificação ≠ Validação
| Verificação                                 | Validação                               |
|---------------------------------------------|-----------------------------------------|
| Estamos construindo o produto corretamente? | Estamos construindo o produto correto?  |
| Conformidade com as especificações          | Atende às necessidades reais do usuário |
| Foco: requisitos e design                   | Foco: expetcativas do cliente           |

Funcionais ≠ Não-Funcionais
> (Coisas que o cliente vê) vs (Coisas que o desenvolvedor vê)

| Funcionais                    | Não-Funcionais                       |
|-------------------------------|--------------------------------------|
| Verificam o que o sistema faz | Verificam como o sistema se comporta |
| Login de usuário              | Desempenho                           |
| Cálculo de desconto           | Segurança                            |
| Busca de produtos             | Escalabilidade                       |

**Exemplo:**
Funcional: "o login funciona? 
Não funcional: "o login responde em menos de 2s?"



## Do menor ao maior escopo

**Unidade:** Serve para verificar qualquer nova funcionalidade,até mesmo as que não são perceptíveis diretamente pelo usuário como funções intermediárias. Como característica dos testes unitários temos a sua grande 
numerosidade e normalmente são automatizados (fundamentalmente caixa branca).
- **Definição do Slide:** Componentes isolados (funções, métodos, classes)

**Integração:** Basicamente nós trabalhamos os componentes do sistema de maneira conjunta, logo o intuito dos testes de integração é verificar se a interface está correta e se o acoplamento dessas interfaces acontecerá sem problemas, com menos testes que os unitários porém ainda automatizados(fundamentalmente caixa preta).
- **Definição do Slide:** Interação entre módulos

**Sistema:** Pode ocorrer de maneira manual, mais custoso e precisa cobrir todos os critérios do sistema.
- **Definição do Slide:** A aplicação completa, de ponta a ponta

**Aceitação:** Pode ser feito diretamente com o cliente (mas não é obrigatóriamente com ele). O ideal é chegar o mais próximo do ambiente real pra realizar o teste, se possível com candidatos semelhantes aos usuários finais 
- **Definição do Slide:** Valida se atende aos requisitos do cliente

Quanto mais abaixo, mais caro é o teste e custoso para a empresa caso algum erro seja identificado.

## Três abordagens complementares

 - **Caixa-preta:** Semelhante ao conceito da caixa-preta do avião. Quando falamos de caixa preta não estamos interessados em como um determinado módulo faz o que ele faz, mas sim interessados em observar a a entrada e saída da interface (mais alinhados com testes de integração).
 - **Caixa-branca:** Baseado na estrutura interna do código, aqui os módulos importam
 - **Caixa-cinza:** Combina especificação com conhecimento parcial da estrutura (pouco usado) 
 
 Caixa-preta: O que faz?
 Caixa-Branca: Como faz?

## Quando cada tipo se aplica

 - **Regressão:** Garante que as mudanças não quebram o que já funcionava
 - **Fumaça:** Verificação rápida das funcionalidades principais
 - **Sanidade:** Confirma que uma correção específica funciona
 - **Exploratório:** teste não sistematizado, sem documentação anterior, vai no "feeling"

| **Test Positivo**                                       | **Teste Negativo**                               |
|---------------------------------------------------------|--------------------------------------------------|
|   Sistema funciona quando usado corretamente            |   Sistema rejeita entrada inválidas              |
| > Login com credenciais válidas, upload de arquivo .jpg | > Login com senha errada, upload de arquivo .exe |

> Testes negativos são essenciais para segurança e robustez.
